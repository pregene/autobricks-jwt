# Service JSON Web Token Revocation

## Purpose

JWT revocation explicitly terminates an active JWT session before its absolute
or idle expiration. A registered WRITE client submits the issued `token_id`
and, when required by the server installation, the complete encrypted token.
Autobricks JWT validates the selected token and its service binding, records the
revoked state in SQLCipher, and removes the active session from Autobricks
Cache.

Revocation does not decrypt fields for the caller, modify a subject Database,
or issue a replacement token.

## Preconditions

Revocation requires:

- A valid registered connection credential.
- An active WRITE `client_id`.
- An active WRITE APIKEY bound to the same service and `client_id`.
- The `JWT_REVOKE` operation.
- The issued `token_id`, plus the complete encrypted `token` when
  `require_token_for_query_and_revoke` is enabled.
- An active session whose service and subject bindings match the WRITE service.

A READ client or READ APIKEY cannot revoke a JWT.

## Request

```json
{
  "operation": "JWT_REVOKE",
  "client_id": "<write-client-id>",
  "apikey": "<write-apikey>",
  "request_id": "<client-request-id>",
  "token_id": "<token-uuid>",
  "token": "<base64url-jwe-compact-token>"
}
```

`request_id` is generated by the client and is unique within that client.
`token_id` is the lookup identifier returned with the token. It accelerates
lookup but does not replace internal validation of the complete encrypted
token.

The request above is mandatory when
`require_token_for_query_and_revoke: true`, which is the secure installation
default. With `require_token_for_query_and_revoke: false`, the caller may omit
`token` to reduce network traffic:

```json
{
  "operation": "JWT_REVOKE",
  "client_id": "<write-client-id>",
  "apikey": "<write-apikey>",
  "request_id": "<client-request-id>",
  "token_id": "<token-uuid>"
}
```

In token-optional mode, Autobricks JWT loads the stored JWE through `token_id`
and validates it before revocation. If the caller supplies `token`, it must
match the stored token and is never ignored.

## Processing

Autobricks JWT processes revocation in this order:

1. Validate the request structure, `request_id`, `token_id`, and request limits.
2. Authenticate the connection identity, active WRITE `client_id`, registered
   service, matching WRITE APIKEY, and `JWT_REVOKE` permission.
3. Locate the active session through the Cache `token_id` MAP.
4. Match the supplied token digest to the active session and SQLCipher record,
   or load the stored token when omission is allowed by the installation.
5. Validate the selected JWE structure, `kid`, key, stored IV, authentication tag,
   claims, audience, expiration, and service binding.
6. Mark the SQLCipher session record `REVOKED` and store `revoked_at`.
7. Remove the active session and its `token_id` MAP entry from Autobricks Cache.
8. Return the revocation result without returning decrypted token fields.

The state transition is fail-closed. Once the durable session is marked
`REVOKED`, the token cannot become active again through Cache reload, Database
history, restart, or Retention behavior.

## Response

```json
{
  "request_id": "<client-request-id>",
  "token_id": "<token-uuid>",
  "status": "REVOKED",
  "revoked_at": "2026-01-01T00:00:00Z"
}
```

The response does not contain the encrypted token, decrypted claims, token key,
IV, or TrueLog receipt.

## State Changes

Successful revocation:

- Preserves the SQLCipher issuance and token-version history.
- Changes the durable session state to `REVOKED` and records `revoked_at`.
- Removes the active Cache session and `token_id` MAP entry.
- Does not delete the token key or historical record required for authorized
  administrative verification.
- Does not change the subject Database.
- Does not extend idle Retention or change the JWT `exp` value.

Later use of the revoked token returns the same
`SESSION_NOT_FOUND_OR_EXPIRED` response used for an expired or nonexistent
session. The service does not disclose that the token previously existed or
was explicitly revoked.

## Concurrency and Idempotency

Only one concurrent revocation can transition an active session to `REVOKED`.
Queries or updates cannot succeed after that transition. A later revocation
request finds no active session and receives `SESSION_NOT_FOUND_OR_EXPIRED`;
it does not create another state transition.

The client-generated `request_id` prevents an ambiguous retry from being
treated as a new unrelated request. It does not reactivate or recreate the
revoked session.

## Logging and Audit

Successful revocation does not create a JWT TrueLog event or append receipt.
The durable SQLCipher state and `revoked_at` value record the session change.

Every classified failure writes its assigned `error_code` and `error_name` to
the operating server's syslog with redacted context. Tokens, APIKEYs, decrypted
claims, token keys, and IVs are never logged.

A revocation request for an already missing, expired, or revoked session uses
`JWT_SESSION_INVALID` with error code `8060`. When audit logging is enabled and
TrueLog is installed and configured, that invalid-session event is appended and
its receipt is stored in the corresponding local record. The event never
distinguishes the underlying session state.

## Errors

The revocation path uses the assigned errors from [ERROR.md](../ERROR.md),
including:

| Code | Name | Revocation use |
| ---: | --- | --- |
| 8001 | `INVALID_REQUEST` | Required request data is missing or inconsistent |
| 8004 | `REQUEST_TOO_LARGE` | The request exceeds its configured limit |
| 8006 | `REQUEST_TIMEOUT` | Revocation exceeds its processing deadline |
| 8030 | `APIKEY_AUTHENTICATION_FAILED` | APIKEY is missing, invalid, revoked, or incorrectly bound |
| 8031 | `APIKEY_OPERATION_FORBIDDEN` | APIKEY does not allow WRITE operations |
| 8032 | `OPERATION_CLASS_MISMATCH` | Credential, client, and APIKEY operation classes disagree |
| 8040 | `SERVICE_NOT_REGISTERED` | No matching active WRITE service registration exists |
| 8041 | `SERVICE_REGISTRATION_INACTIVE` | The matching service registration is inactive |
| 8060 | `SESSION_NOT_FOUND_OR_EXPIRED` | The session is missing, expired, or no longer active |
| 8061 | `JWT_INVALID` | The token is malformed, mismatched, or fails integrity validation |
| 8062 | `JWT_AUDIENCE_INVALID` | The token is not valid for the authenticated service |
| 8081 | `DATABASE_OPERATION_FAILED` | The durable revoked state could not be recorded |
| 8082 | `CACHE_UNAVAILABLE` | The active Cache session could not be invalidated safely |
| 8084 | `KEY_STORE_UNAVAILABLE` | The protected token key required for validation is unavailable |

Internal errors are mapped to the safe response defined by `ERROR.md`. A
failed state transition never returns a successful revocation result.

## Security Boundaries

- Revocation requires the complete WRITE authorization chain.
- A READ credential cannot revoke or otherwise change session state.
- A supplied token and `token_id` must match the same active session. When the
  token is omitted, the installation must explicitly enable token-optional
  query and revocation requests.
- A WRITE client cannot revoke a token bound to another service.
- Revocation never returns decrypted JWT content.
- A revoked session cannot be restored from SQLCipher history or Cache
  persistence.
- Historical retention supports administrative verification but grants no
  runtime token access.
